# Performance Investigation Report

**Date:** 2026-09-13
**Analysis window:** 7 days (2026-09-06 to 2026-09-13)
**Project:** fishbone-wins-pool
**Spec:** docs/superpowers/specs/2026-09-13-performance-investigation-design.md

## Motivating Finding

The `winspool` Cloud Run service (region `us-east1`) has:
- `autoscaling.knative.dev/maxScale=1` — capped at exactly one instance, never scales out.
- No `autoscaling.knative.dev/minScale` annotation — sits at the Cloud Run default of 0, so the service scales to zero when idle and cold-starts on the next request.

Confirmed live via `gcloud run services describe winspool --region=us-east1 --format="value(spec.template.metadata.annotations)"` on 2026-09-13. Full annotation string: `autoscaling.knative.dev/maxScale=1;run.googleapis.com/client-name=gcloud;run.googleapis.com/client-version=559.0.0;run.googleapis.com/startup-cpu-boost=true`.

## Backend / Cloud Run

- **Request latency (2xx, 7-day window):** p50 = `41.3` ms, p95 = `984.7` ms.
- **Cold-start (container startup) latency:** p95 = `20111.6` ms (worst of the window, revision `winspool-00097-8g7`) across `13` revision-entries in the window (range 7146.9-20111.6 ms; each entry is one revision's startup event, not a count of scale-from-zero cold starts experienced by users).
- **Time at zero instances:** `0` of `112` hourly samples (`0`%) had zero running instances; max concurrent instance count observed was `2` (briefly, consistent with revision rollover overlap, not sustained scale-out — `maxScale=1` still caps steady-state capacity at one instance). Note the window returned 112 hourly points rather than the expected ~168 for a 7-day span; this was not investigated further per instructions not to force a different query shape.
- **Peak concurrent requests (any single hour):** `11.5` (hourly p95-aligned, max across the 7-day window). Note: the brief's original query used `ALIGN_MAX`, which the Cloud Monitoring API rejected (`400 INVALID_ARGUMENT: "The aligner cannot be applied to metrics with kind DELTA and value type DISTRIBUTION."`) because `run.googleapis.com/container/max_request_concurrencies` is a DELTA-kind, DISTRIBUTION-valued metric and `ALIGN_MAX` only works on GAUGE/numeric-valued metrics. Re-run with `ALIGN_PERCENTILE_95` (chosen for consistency with the Step 2 cold-start query's aligner; `ALIGN_PERCENTILE_99` would also have been valid) in place of `ALIGN_MAX`, same filter/window/`REDUCE_MAX` otherwise, which returned real data: 112 hourly points, max value `11.5`, next-highest `11.1`, `11.1`, `9.7`, `7.7`.

**Interpretation:** The data does not support "scale-to-zero cold starts are causing the p95 latency spikes" as stated. The service spent 0% of the 7-day window at zero instances — it did not actually scale to zero in this period despite having no `minScale` floor, so idle-triggered cold starts were rare-to-nonexistent here. The 13 measured startup events (7.1-20.1 seconds each) instead line up with revision deployments during the week, not traffic-driven scale-ups. Critically, those startup latencies (7-20 *seconds*) are 10-20x larger than the p95 *request* latency (985 ms), meaning a cold start — if a user request landed during one — would dominate that request's latency far beyond what shows up at p95; the fact that p95 is only ~1 second suggests either very few user requests actually hit a cold instance in this window, or Cloud Run's startup-cpu-boost plus low traffic volume kept most requests off the small number of cold windows. The 24x p50-to-p95 gap (41 ms to 985 ms) is real but likely reflects a mix of a few slow endpoints and/or the rare cold-start-affected request, not a systemic scale-to-zero problem in the current traffic pattern. Peak concurrency (11.5, hourly p95) is far below Cloud Run's default per-instance limit of 80 — nowhere close to saturating a single instance — so `maxScale=1` is **not currently a live bottleneck**: it remains a real latent risk if traffic grows substantially (e.g. a full 10-player live draft with many concurrent connections), but today's traffic pattern doesn't come close to exercising it. The cold-start theory as the primary driver of the motivating finding is not well corroborated by this window's data either.

**Live draft WebSocket (`routes/draft_routes.py`):** Every inbound WS message that mutates or re-renders state (`pick`, `force_pick`, `undo_pick`, `reset_pick`) calls `services/draft_service.py::load_draft_state()`. That function has its own process-local singleton (`_CACHED_DRAFT_STATE`, `draft_service.py:13,48-56`) that serves a cheap in-memory `deepcopy` when `year is None` and the singleton is warm — but `save_pick()`/`undo_pick()`/`reset_pick()` each set `_CACHED_DRAFT_STATE = None` (`draft_service.py:230,236,257`). Tracing one `pick` message end-to-end (`draft_routes.py:731-771`): the frontend's pick message carries no `year` field (`static/js/main.js:796`: `{action:'pick', playerId, team}`), so `target_year` stays `None` for the whole exchange. The *first* `load_draft_state()` call (state fetch for validation) hits the fast in-memory path, since the previous pick's rebuild left the singleton warm. `get_config_settings()` is then called directly in the handler for the "is the draft open" check (`draft_routes.py:758`) — an uncached Firestore read regardless of cache warmth. Once the pick is validated, `save_pick()` nukes the singleton, and the *second* `load_draft_state()` call (to build the broadcast state) is forced into a full, uncached rebuild: a direct `get_collection_df('draft_order')` scan to resolve the season (`draft_service.py:67`, skipped only if a `year` was explicitly supplied), then both `get_season_projection_blended()` (`draft_service.py:153`) and `get_season_projection_dual()` (`draft_service.py:159`) — which independently and redundantly each re-fetch `preseason_predictions` and `consensus_projections` uncached (4 raw Firestore reads total, since the two functions duplicate each other's work rather than sharing one fetch), plus a second uncached `get_config_settings()` read for the pick-timer-open check (`draft_service.py:190`) and a `metadata/draft_timer_{season}` read-then-conditional-write (`draft_service.py:192-201`). Net effect: one full rebuild (not two) happens per pick, but it alone does roughly 7-8 direct, uncached Firestore round-trips (season lookup, 4x projection reads, 1x config read, 1-2x timer metadata), plus the handler's own separate `get_config_settings()` call before that rebuild — around 8-9 so far, independent of how many of the up to 10 players are connected. That count still excludes chat: `_broadcast_pick_messages()` (`draft_routes.py:500-542`) calls `chat_service.py`'s `post_system_message()` (`chat_service.py:59-77`) twice on (almost) every pick — once to announce the pick, once for the next player's "on the clock" message (skipped only on the 30th, final pick, since there's no next player to notify) — and each call is itself two separate Firestore RPCs, not one: `ref.add(data)` (a write) followed by a separate `doc_ref.get()` (a read), because `CollectionReference.add()` returns only a write-result timestamp and a bare `DocumentReference`, not the field data, so the read-back is a genuine second network round-trip, executed directly and synchronously in the async WS handler rather than offloaded to a thread-pool executor. Folding those in (2 calls × 2 RPCs = 4 RPCs on a typical pick) brings the real per-pick total to roughly **12-13** uncached Firestore round-trips — or **10-11** only on pick #30, where the second chat call is skipped. The WebSocket fan-out itself (`ConnectionManager.broadcast()`) is pure in-memory `send_json` and scales fine with connection count; the per-pick Firestore work is what doesn't obviously scale, and because a draft is a serialized sequence of exactly 30 picks, this is a fixed roughly **360-390-call** Firestore tax per draft (12-13 × 30) regardless of how many players are connected. This is a code-level read, not a measured one — Task 4's aggregate metrics should confirm whether this shows up as real latency or Firestore cost in practice, and whether `switch_season` (which does pin a non-`None` `year` and would change this trace) is used during real drafts.

**Mock draft (`routes/mock_draft_routes.py` / `services/mock_draft_service.py`):** This is a separate, login-free, unauthenticated surface with its own uncached hot path, omitted from the original inventory. `GET /api/mock-draft/setup` calls `get_pick_sequence()` (`mock_draft_service.py:36`), which does the direct, uncached `draft_order_rules` fetch noted in the table above, plus `get_projection_season()` (`mock_draft_service.py:75-76`), which does two more uncached, unfiltered reads of `preseason_predictions` and `consensus_projections` to find the latest projected season — so every `/setup` call costs ~3 uncached reads before any admin-only projection payload is even considered. The bigger cost is per-pick: `POST /api/mock-draft/pick` (`mock_draft_routes.py:117-131`) calls `bot_pick()` (`mock_draft_service.py:130`) for every bot-controlled slot, and unless the pity mechanic forces a wildcard, `bot_pick()` calls `get_season_projection_legacy_shape(season)` (`data_service.py:462`), which itself does two uncached reads (`get_preseason_predictions()` + `get_consensus_projections()`, `data_service.py:388,410`) on **every single call** — no caching or memoization across picks within a session. A full 10-player, 30-pick mock draft has up to ~27 bot picks (1 human player drafting 3 teams), so this is roughly 1 (`draft_order_rules`) + 2 (`get_projection_season`) + up to 27 × 2 = **~57 uncached Firestore reads across one mock-draft session** — a second uncached hot path of comparable interest to the live-draft WebSocket one above, and entirely public/unauthenticated.

### Cache TTL sizing (`cache_service.py:118`, `_CACHE_TTL_SECONDS`)

Current value: 3600s (1 hour), shared by `data_service.py::load_data()`'s main cache and `cache_service.py`'s own cached reads. The inline comment's stated rationale: "long enough to avoid Firestore spam on every request, short enough to catch same-day data changes."

**What this TTL actually governs — a much smaller slice of traffic than it sounds like.** Per the web-app inventory above, `_CACHE_TTL_SECONDS` only gates `load_data()`'s bundle (`nfl_standings`, `nfl_teams`, `nfl_games`, `players`, `draft_order`, `draft_results`, `draft_order_rules`) and the warm-cache-first `players` lookup in `_get_players_df()` — the base data behind standings/schedule/history pages. Every other row in that table is explicitly **uncached**, bypassing `load_data()` and this TTL entirely regardless of its value: `preseason_predictions`, `consensus_projections`, the separate `draft_order`/`draft_order_rules` fetches used for season resolution and mock-draft setup, `game_predictions`, `prediction_features`, `elo_history` and `nn_weekly_accuracy` (both full-collection `.stream()` reads on every admin page load), `config`/`metadata` docs, and chat. So does the live-draft WebSocket's per-pick rebuild and the mock-draft bot-pick loop — the two hottest paths this report found (**~360-390 Firestore round-trips per 30-pick draft**, **~57 reads per mock-draft session**, per the paragraphs above) do not read through `load_data()` at all.

**The "short enough to catch same-day changes" half of the rationale is largely handled by a different mechanism already.** `load_data()` also polls `metadata/cache_control` every `_REMOTE_CHECK_INTERVAL` (60s, `cache_service.py:120`) and clears the in-memory cache early if a remote `last_update` timestamp is newer than the cache's own — driven by `signal_data_update()` calls in `db_service.py` (confirmed at lines 273, 384, 431, 468, 645, 714 — player/draft/season writes) and in `services/live_score_service.py:135-136` (fired from `sync_live_scores.py` when its own rebuild changes anything). For every write path that calls it, effective staleness is bounded by ~60 seconds, not 3600 — the 1-hour number is a fallback ceiling for a signal that's already firing, not the routine invalidation path the comment implies.

**One real gap found while checking this, unrelated to the TTL's size:** `scripts/daily_nfl_sync.py`'s own `batch_upload()` — the write path `winspool-sync-daily` uses for its full unfiltered `nfl_games`/`nfl_standings` overwrite (Task 4's scheduled-jobs table; confirmed 4 runs on 2026-09-13 at 09:00/15:45/19:10/23:05 UTC) — never calls `signal_data_update()`, unlike `live_score_service.py`'s equivalent write path. That means the *one* write path where the full 3600s genuinely is the operative staleness bound (not a rarely-hit fallback) is exactly the `load_data()` bundle's own primary data source. In practice this is low-stakes: `winspool-live-scores` re-covers the same two collections every ~5 minutes during live windows and does signal, so the daily job's un-signaled writes are backstopped by a faster, signaling path whenever games are actually live.

**Recommendation: keep `_CACHE_TTL_SECONDS` at 3600s, but treat it as a non-issue relative to this report's real findings, not as something to tune.** Three reasons, each tied to numbers already in this report:
1. **It isn't the lever on the report's actual read-volume problem.** The aggregate 7-day total above is `2,676,060` reads / `136,071` writes, and this section's own Interpretation attributes the read volume to the uncached direct-read paths documented earlier in this section — the live-draft WS's ~360-390 calls/draft and the mock-draft's ~57 reads/session chief among them — none of which pass through `_CACHE_TTL_SECONDS` at all. Raising or lowering this one number would not touch that traffic; it only resizes the cache for the cheapest, lowest-frequency slice of the app (standings/schedule/history pages).
2. **Live-draft freshness needs nothing from this TTL.** Confirming the brief's framing in Step 2: `load_draft_state()`'s per-pick rebuild is invalidated synchronously by `save_pick()`/`undo_pick()`/`reset_pick()` setting `_CACHED_DRAFT_STATE = None` (`draft_service.py:230,236,257`), and reads `preseason_predictions`/`consensus_projections`/`config` directly and uncached on every rebuild — the draft flow gets sub-second freshness through its own singleton-invalidation and direct-read pattern, entirely independent of `_CACHE_TTL_SECONDS`.
3. **The one place 3600s is a real (not fallback) staleness bound is low-stakes and already backstopped.** The `daily_nfl_sync.py` signal gap above means standings/schedule data pushed by `winspool-sync-daily` could sit stale in-cache for up to an hour — but `winspool-live-scores` (which does signal) re-covers the same collections on a 5-minute cadence whenever games are live, so the exposure window in practice is much smaller than 3600s implies.

Lowering the TTL would add Firestore load to the one path in this inventory that's already cheap, for no measurable correctness gain. Raising it would only matter for the one signal-omitting write path identified above, and would widen that gap rather than close it. The actionable follow-ups this analysis surfaces are process fixes, not a TTL change: (a) add a `signal_data_update()` call to `daily_nfl_sync.py`'s `batch_upload()` to close the one real gap found here, and (b) address the uncached direct-read paths (live-draft WS, mock draft, `elo_history`/`nn_weekly_accuracy` full-collection streams) that this section's Interpretation already flags as the plausible driver of the 2.68M-read week — that's where read-volume reduction actually lives, not in `_CACHE_TTL_SECONDS`.
