# Performance Investigation Report

## Motivating Finding

The `winspool` Cloud Run service (region `us-east1`) has:
- `autoscaling.knative.dev/maxScale=1` — capped at exactly one instance, never scales out.
- No `autoscaling.knative.dev/minScale` annotation — sits at the Cloud Run default of 0, so the service scales to zero when idle and cold-starts on the next request.

Confirmed live via `gcloud run services describe winspool --region=us-east1 --format="value(spec.template.metadata.annotations)"` on 2026-09-13. Full annotation string: `autoscaling.knative.dev/maxScale=1;run.googleapis.com/client-name=gcloud;run.googleapis.com/client-version=559.0.0;run.googleapis.com/startup-cpu-boost=true`.

## Backend / Cloud Run

- **Request latency (2xx, 7-day window):** p50 = `41.3` ms, p95 = `984.7` ms.
- **Cold-start (container startup) latency:** p95 = `20111.6` ms (worst of the window, revision `winspool-00097-8g7`) across `13` revision-entries in the window (range 7146.9-20111.6 ms; each entry is one revision's startup event, not a count of scale-from-zero cold starts experienced by users).
- **Time at zero instances:** `0` of the `112` *sampled* hourly points had zero running instances; max concurrent instance count observed across those samples was `2` (briefly, consistent with revision rollover overlap, not sustained scale-out — `maxScale=1` still caps steady-state capacity at one instance). **This does not establish that the service never scaled to zero.** The window returned only 112 hourly points rather than the expected ~168 for a full 7×24 span — a gap of 56 hours — and `run.googleapis.com/container/instance_count` is emitted *by* running container instances: a period with zero running instances produces no sample at all (a gap in the time series), not a reported value of `0`. 56 missing hours is exactly 8 hours/day, the classic shape of a nightly idle window, making the missing samples a plausible candidate for exactly the scale-to-zero periods this query was meant to detect. This gap was not resolved by this investigation — no attempt was made to force a different query shape or backfill the missing hours, and no instruction anywhere in this investigation's plan or brief called for leaving it uninvestigated; that was simply not done.
- **Peak concurrent requests (any single hour):** `11.5` (hourly p95-aligned, max across the 7-day window). Note: the brief's original query used `ALIGN_MAX`, which the Cloud Monitoring API rejected (`400 INVALID_ARGUMENT: "The aligner cannot be applied to metrics with kind DELTA and value type DISTRIBUTION."`) because `run.googleapis.com/container/max_request_concurrencies` is a DELTA-kind, DISTRIBUTION-valued metric and `ALIGN_MAX` only works on GAUGE/numeric-valued metrics. Re-run with `ALIGN_PERCENTILE_95` (chosen for consistency with the Step 2 cold-start query's aligner; `ALIGN_PERCENTILE_99` would also have been valid) in place of `ALIGN_MAX`, same filter/window/`REDUCE_MAX` otherwise, which returned real data: 112 hourly points, max value `11.5`, next-highest `11.1`, `11.1`, `9.7`, `7.7`.

**Interpretation:** The data does not support "scale-to-zero cold starts are causing the p95 latency spikes" as stated — but it also does not rule that out. The service showed 0% of *sampled* hours at zero instances, but as noted above, 56 of the expected 168 hourly samples (~8 hours/day) are simply missing rather than confirmed non-zero, because Cloud Run's `instance_count` metric reports gaps rather than zero-valued samples when nothing is running — whether the service scaled to zero during those missing hours is not established by this window's data either way. The 13 measured startup events (7.1-20.1 seconds each) are consistent with lining up with revision deployments during the week rather than traffic-driven scale-ups — each `startup_latencies` entry is revision-keyed, one per distinct revision that started up, and 13 distinct revisions in the window is consistent with that reading — but this was not directly verified against actual revision-creation timestamps, and the metric alone cannot distinguish a deployment-triggered start from an idle-triggered one. Critically, those startup latencies (7-20 *seconds*) are 10-20x larger than the p95 *request* latency (985 ms), meaning a cold start — if a user request landed during one — would dominate that request's latency far beyond what shows up at p95; the fact that p95 is only ~1 second suggests either very few user requests actually hit a cold instance in this window, or Cloud Run's startup-cpu-boost plus low traffic volume kept most requests off the small number of cold windows. The 24x p50-to-p95 gap (41 ms to 985 ms) is real but likely reflects a mix of a few slow endpoints and/or the rare cold-start-affected request, not a confirmed systemic scale-to-zero problem in the current traffic pattern. Peak concurrency (11.5, hourly p95) is far below Cloud Run's default per-instance limit of 80 — nowhere close to saturating a single instance — so `maxScale=1` is **not currently a live bottleneck**: it remains a real latent risk if traffic grows substantially (e.g. a full 10-player live draft with many concurrent connections), but today's traffic pattern doesn't come close to exercising it. The cold-start theory as the primary driver of the motivating finding is neither confirmed nor ruled out by this window's data.

**Live draft WebSocket (`routes/draft_routes.py`):** Every inbound WS message that mutates or re-renders state (`pick`, `force_pick`, `undo_pick`, `reset_pick`) calls `services/draft_service.py::load_draft_state()`. That function has its own process-local singleton (`_CACHED_DRAFT_STATE`, `draft_service.py:13,48-56`) that serves a cheap in-memory `deepcopy` when `year is None` and the singleton is warm — but `save_pick()`/`undo_pick()`/`reset_pick()` each set `_CACHED_DRAFT_STATE = None` (`draft_service.py:230,236,257`). Tracing one `pick` message end-to-end (`draft_routes.py:731-771`): the frontend's pick message carries no `year` field (`static/js/main.js:796`: `{action:'pick', playerId, team}`), so `target_year` stays `None` for the whole exchange. The *first* `load_draft_state()` call (state fetch for validation) hits the fast in-memory path, since the previous pick's rebuild left the singleton warm. `get_config_settings()` is then called directly in the handler for the "is the draft open" check (`draft_routes.py:758`) — an uncached Firestore read regardless of cache warmth. Once the pick is validated, `save_pick()` nukes the singleton, and the *second* `load_draft_state()` call (to build the broadcast state) is forced into a full, uncached rebuild: a direct `get_collection_df('draft_order')` scan to resolve the season (`draft_service.py:67`, skipped only if a `year` was explicitly supplied), then both `get_season_projection_blended()` (`draft_service.py:153`) and `get_season_projection_dual()` (`draft_service.py:159`) — which independently and redundantly each re-fetch `preseason_predictions` and `consensus_projections` uncached (4 raw Firestore reads total, since the two functions duplicate each other's work rather than sharing one fetch), plus a second uncached `get_config_settings()` read for the pick-timer-open check (`draft_service.py:190`) and a `metadata/draft_timer_{season}` read-then-conditional-write (`draft_service.py:192-201`). Net effect: one full rebuild (not two) happens per pick, but it alone does roughly 7-8 direct, uncached Firestore round-trips (season lookup, 4x projection reads, 1x config read, 1-2x timer metadata), plus the handler's own separate `get_config_settings()` call before that rebuild — around 8-9 so far, independent of how many of the up to 10 players are connected. That count still excludes chat: `_broadcast_pick_messages()` (`draft_routes.py:500-542`) calls `chat_service.py`'s `post_system_message()` (`chat_service.py:59-77`) twice on (almost) every pick — once to announce the pick, once for the next player's "on the clock" message (skipped only on the 30th, final pick, since there's no next player to notify) — and each call is itself two separate Firestore RPCs, not one: `ref.add(data)` (a write) followed by a separate `doc_ref.get()` (a read), because `CollectionReference.add()` returns only a write-result timestamp and a bare `DocumentReference`, not the field data, so the read-back is a genuine second network round-trip, executed directly and synchronously in the async WS handler rather than offloaded to a thread-pool executor. On that same "on the clock" branch, there is a further uncached read this report's own scheduled/uncached-paths table above already documents but hadn't folded into this running total: `_broadcast_pick_messages()` (`draft_routes.py:547-555`) also fires `_send_push_sync()` → `services/push_service.py::send_push_notification()` for the next player, and that function does an unconditional `get_db().collection("players").document(...).get()` (`push_service.py:40`) to look up the player's stored push subscription before sending — whenever VAPID push credentials are configured (as CLAUDE.md documents they are). That's one more Firestore read, gated by the same `new_active <= 30` check as the "on the clock" chat message, so it's likewise skipped only on pick #30. Folding both the chat double-RPCs and this push-lookup read in (2 chat calls × 2 RPCs = 4 RPCs, plus 1 push read, on a typical pick) brings the real per-pick total to roughly **13-14** uncached Firestore round-trips — still **10-11** only on pick #30, where the second chat call and the push lookup are both skipped. The WebSocket fan-out itself (`ConnectionManager.broadcast()`) is pure in-memory `send_json` and scales fine with connection count; the per-pick Firestore work is what doesn't obviously scale, and because a draft is a serialized sequence of exactly 30 picks, this is a fixed roughly **390-420-call** Firestore tax per draft (13-14 × 30) regardless of how many players are connected. This is a code-level read, not a measured one — Task 4's aggregate metrics should confirm whether this shows up as real latency or Firestore cost in practice, and whether `switch_season` (which does pin a non-`None` `year` and would change this trace) is used during real drafts.

**Mock draft (`routes/mock_draft_routes.py` / `services/mock_draft_service.py`):** This is a separate, login-free, unauthenticated surface with its own uncached hot path, omitted from the original inventory. `GET /api/mock-draft/setup` calls `get_pick_sequence()` (`mock_draft_service.py:36`), which does the direct, uncached `draft_order_rules` fetch noted in the table above, plus `get_projection_season()` (`mock_draft_service.py:75-76`), which does two more uncached, unfiltered reads of `preseason_predictions` and `consensus_projections` to find the latest projected season — so every `/setup` call costs ~3 uncached reads before any admin-only projection payload is even considered. The bigger cost is per-pick: `POST /api/mock-draft/pick` (`mock_draft_routes.py:117-131`) calls `bot_pick()` (`mock_draft_service.py:130`) for every bot-controlled slot, and unless the pity mechanic forces a wildcard, `bot_pick()` calls `get_season_projection_legacy_shape(season)` (`data_service.py:462`), which itself does two uncached reads (`get_preseason_predictions()` + `get_consensus_projections()`, `data_service.py:388,410`) on **every single call** — no caching or memoization across picks within a session. A full 10-player, 30-pick mock draft has up to ~27 bot picks (1 human player drafting 3 teams), so this is roughly 1 (`draft_order_rules`) + 2 (`get_projection_season`) + up to 27 × 2 = **~57 uncached Firestore reads across one mock-draft session** — a second uncached hot path of comparable interest to the live-draft WebSocket one above, and entirely public/unauthenticated.

**Operational anomaly — `winspool-live-scores` did not run for ~18 days:** real execution history shows **zero executions of `winspool-live-scores` from 2026-08-22 to 2026-09-09**, with continuous, exact 5-minute-spaced execution resuming only on 2026-09-10 (see the "Real cadence" cell above, where this gap is also the reason 1,102 rather than 2,016 executions is used in the write-volume arithmetic below). This is exactly why a liveness/heartbeat-style alert (already recommended in the Recommendations threshold list below) is needed as a complement to the existing policy, not a duplicate of it.

### Aggregate project-wide volume (7-day window)

Pulled via the Cloud Monitoring REST API (`firestore.googleapis.com/document/{read,write,delete}_count`, `ALIGN_SUM` + `REDUCE_SUM` over the full window), 2026-09-07T00:20:23Z to 2026-09-14T00:20:23Z:

- Document reads: `2,676,060`
- Document writes: `136,071`
- Document deletes: `29`

**Interpretation:** The estimated ~90,000-95,000 writes attributable to `winspool-live-scores` alone (above) account for roughly two-thirds of the measured 136,071 project-wide total — plausible and well-corroborated: the job's own code comment in `sync_live_scores.py` documents that an earlier, unnarrowed version of this exact job was independently measured at ~179,000 writes/*day* (~9x the Firestore free-tier daily quota), which is exactly why the current trailing-7-day-window narrowing exists. The two daily jobs contribute comparatively little by count despite `winspool-sync-daily` pushing a full, unfiltered overwrite of every game and team-season since 2013 — because they fire only a handful of times a day (one base cron run plus a few kickoff-triggered runs on game days) versus live-scores' up to 288 opportunities per day.

The 2.68M reads are much harder to attribute, and the report's own magnitude test — correctly used to eliminate the scheduled jobs above — has to be applied to the web app's uncached paths just as honestly. None of the 4 scheduled jobs perform meaningful per-document reads in their own code (they are overwhelmingly write/batch-write paths, and the only scheduled-job read pattern found — `cache_builder.py`'s ~32-doc lock-check query before writing `preseason_predictions`, once/day/season — is far too small to explain a multi-million-read week). But the web app's own uncached hot paths documented above in this section are *also* too small, by the same test: 2,676,060 reads/week is ≈382,300 reads/day. The live-draft WS pick path is a once-per-season event (~30 picks × ~13-14 reads ≈ 390-420 reads *for the entire season's one draft*, not per day). The mock-draft session (~57 reads/session) would need on the order of 6,700 sessions *every single day* to reach 382,300 reads on its own — implausible for a private ~10-player pool's public practice tool. The admin `elo_history`/`nn_weekly_accuracy` full-collection streams (~21 season-docs each per admin page load) would need roughly 9,000 admin page loads/day. Even generously summing all three at once (a handful of drafts across the year, a few dozen mock-draft sessions, and a handful of admin loads per day) lands in the low thousands of reads/day at most — two to three orders of magnitude short of 382,300/day. These paths are still worth fixing on their own merits (they are genuinely wasteful, uncached, and duplicate-fetching), but they do not explain the aggregate read volume.

A more plausible, but still unmeasured, candidate exists in a mechanism this report has not yet costed from a read-amplification angle: `services/live_score_service.py` calls `signal_data_update()` (via `db_service.py`) whenever `winspool-live-scores`' rebuild changes anything — up to 288 times/day per the Scheduled Jobs table above. `data_service.py::load_data()` checks that signal at most once per `_REMOTE_CHECK_INTERVAL` (60s), and when it sees a newer remote timestamp, calls `clear_data_cache()` **with no year argument** (`data_service.py:78`) — which, per `cache_service.py::clear_data_cache()`, wipes the *entire* `_DATA_CACHE`, every cached year plus the unscoped `'all'` key, not just the year that changed. The next `load_data(year=None)` call (the unscoped/master bundle several pages resolve through) then re-fetches `nfl_games`/`nfl_standings` with `season_filter=None` (`data_service.py:147,153-161`) — i.e. the entire history since `POOL_START_YEAR=2013`, unfiltered, not just the current season. Rough per-rebuild cost: roughly 285 games/season × ~13 seasons ≈ 3,700 `nfl_games` docs, plus ~32 teams × 13 seasons ≈ 420 `nfl_standings` docs, plus the smaller `players`/`draft_order`/`draft_results`/`draft_order_rules`/`nfl_teams` collections — on the order of 4,000-4,500 document reads for a single unscoped rebuild. If that unscoped rebuild is triggered anywhere from a few dozen to roughly 100 times/day (bounded by how often the 60s-throttled check actually observes a newer signal, and by how many distinct year-keyed caches independently need rebuilding after each wipe), that alone lands in the 100,000-400,000+ reads/day range — the right order of magnitude to explain the aggregate figure. This is confirmed as a real code pattern by reading `services/data_service.py` and `services/cache_service.py` directly, but **it has not been measured**: this investigation did not instrument how often the invalidation actually fires in production or how many rebuilds it triggers, so it remains the leading untested candidate, not a confirmed attribution. Cloud Monitoring's Firestore metrics have no per-caller breakdown, so a definitive split between this pattern, the uncached hot paths above, and any other unexamined path isn't possible from these numbers alone.

For comparison: the measured 382,300 reads/day is itself roughly **7.6x** the Firestore free tier's 50,000-reads/day daily allowance — the same kind of over-limit signal this report's write-volume comparison already flagged above for `winspool-live-scores`' historical write pattern.

### Cache TTL sizing (`cache_service.py:118`, `_CACHE_TTL_SECONDS`)

Current value: 3600s (1 hour), shared by `data_service.py::load_data()`'s main cache and `cache_service.py`'s own cached reads. The inline comment's stated rationale: "long enough to avoid Firestore spam on every request, short enough to catch same-day data changes."

**What this TTL actually governs — a much smaller slice of traffic than it sounds like.** Per the web-app inventory above, `_CACHE_TTL_SECONDS` only gates `load_data()`'s bundle (`nfl_standings`, `nfl_teams`, `nfl_games`, `players`, `draft_order`, `draft_results`, `draft_order_rules`) and the warm-cache-first `players` lookup in `_get_players_df()` — the base data behind standings/schedule/history pages. Every other row in that table is explicitly **uncached**, bypassing `load_data()` and this TTL entirely regardless of its value: `preseason_predictions`, `consensus_projections`, the separate `draft_order`/`draft_order_rules` fetches used for season resolution and mock-draft setup, `game_predictions`, `prediction_features`, `elo_history` and `nn_weekly_accuracy` (both full-collection `.stream()` reads on every admin page load), `config`/`metadata` docs, and chat. So does the live-draft WebSocket's per-pick rebuild and the mock-draft bot-pick loop — the two hottest per-request Firestore paths this report found (**~390-420 Firestore round-trips per 30-pick draft**, **~57 reads per mock-draft session**, per the paragraphs above) do not read through `load_data()` at all. Note the mechanism this TTL is *part of* — `load_data()`'s remote-signal check and `clear_data_cache()` — is a separate story from the TTL value itself: the Aggregate volume Interpretation above identifies an unscoped `clear_data_cache()` call (no year argument) followed by an unfiltered master-key refetch as the leading untested candidate for the 2.68M-read week. Raising or lowering `_CACHE_TTL_SECONDS` would not touch that pattern either — it's driven by the signal-check/invalidation logic, not the TTL fallback.

**The "short enough to catch same-day changes" half of the rationale is largely handled by a different mechanism already.** `load_data()` also polls `metadata/cache_control` every `_REMOTE_CHECK_INTERVAL` (60s, `cache_service.py:120`) and clears the in-memory cache early if a remote `last_update` timestamp is newer than the cache's own — driven by `signal_data_update()` calls in `db_service.py` (confirmed at lines 273, 384, 431, 468, 645, 714 — player/draft/season writes) and in `services/live_score_service.py:135-136` (fired from `sync_live_scores.py` when its own rebuild changes anything). For every write path that calls it, effective staleness is bounded by ~60 seconds, not 3600 — the 1-hour number is a fallback ceiling for a signal that's already firing, not the routine invalidation path the comment implies.

**Checked for a genuine gap here and found none.** `scripts/daily_nfl_sync.py`'s own `batch_upload()` is just a generic upload helper; the function `winspool-sync-daily` actually runs is `sync_nfl_data()`, and it does signal cache invalidation on every run — lines 151-152 write `db.collection("metadata").document("cache_control").set({"last_update": time.time()})` directly, which is byte-for-byte the same write `signal_data_update()` (`db_service.py:119-130`) performs. The job just inlines the write instead of importing and calling the named helper, which is why grepping the file for the literal string `signal_data_update` (the original check here) found nothing — a false negative for the real question of whether the write path signals invalidation. So both writers of the `nfl_games`/`nfl_standings` collections that feed `load_data()`'s bundle — `winspool-sync-daily` (inlined) and `winspool-live-scores` (via the named helper) — signal on every write, matching what Task 4's scheduled-jobs table already shows for `winspool-sync-daily`'s `metadata/cache_control` writes. Cross-checking the rest of the `load_data()` bundle's collections against the confirmed `signal_data_update()` call sites above (players/draft/season writes at `db_service.py:273,384,431,468,645,714`) turns up no other un-signaled writer either. **There is no write path in this inventory where the full 3600s TTL is actually the operative staleness bound** — every writer of data that flows through `load_data()`'s cache signals invalidation, so the ~60s remote-check interval is the practical bound everywhere, not just for a subset of write paths.

**Recommendation: keep `_CACHE_TTL_SECONDS` at 3600s, but treat it as a non-issue relative to this report's real findings, not as something to tune.** Three reasons, each tied to numbers already in this report:
1. **It isn't the lever on the report's actual read-volume problem, whichever source turns out to explain it.** The aggregate 7-day total above is `2,676,060` reads / `136,071` writes. This section's own Interpretation shows the uncached direct-read paths documented earlier in this section — the live-draft WS's ~390-420 calls/draft and the mock-draft's ~57 reads/session chief among them — are themselves too small to explain that volume, and instead points at an unscoped `clear_data_cache()` → unfiltered master-key refetch pattern as the leading untested candidate. None of these — the uncached hot paths, or the invalidation-triggered refetch — pass through `_CACHE_TTL_SECONDS` at all. Raising or lowering this one number would not touch any of that traffic; it only resizes the cache for the cheapest, lowest-frequency slice of the app (standings/schedule/history pages).
2. **Live-draft freshness needs nothing from this TTL.** Confirming the brief's framing in Step 2: `load_draft_state()`'s per-pick rebuild is invalidated synchronously by `save_pick()`/`undo_pick()`/`reset_pick()` setting `_CACHED_DRAFT_STATE = None` (`draft_service.py:230,236,257`), and reads `preseason_predictions`/`consensus_projections`/`config` directly and uncached on every rebuild — the draft flow gets sub-second freshness through its own singleton-invalidation and direct-read pattern, entirely independent of `_CACHE_TTL_SECONDS`.
3. **No write path in this inventory is actually exposed to the full 3600s bound.** Every writer feeding the `load_data()` bundle signals cache invalidation — either via `signal_data_update()` directly, or (as with `daily_nfl_sync.py`) an inlined write to the same `metadata/cache_control` document — so the ~60s remote-check interval, not 3600s, is the practical staleness bound throughout.

Lowering the TTL would add Firestore load to the one path in this inventory that's already cheap, for no measurable correctness gain. Raising it would cost nothing either, since no write path actually relies on the 3600s fallback. The actionable follow-up this analysis surfaces is a process fix, not a TTL change: address the uncached direct-read paths (live-draft WS, mock draft, `elo_history`/`nn_weekly_accuracy` full-collection streams) on their own merits — they're wasteful regardless — and, more urgently, investigate/measure the unscoped `clear_data_cache()` → unfiltered master-key refetch pattern the Aggregate volume Interpretation above flags as the leading untested candidate for the 2.68M-read week. Neither lives in `_CACHE_TTL_SECONDS`.

## Recommendations

Ordered by expected impact / effort ratio, highest first. None of these are applied as part of this investigation — see the spec's "Report + recommendations only" constraint.

**On the motivating finding first, since it sets the frame for everything below:** the investigation set out to test whether `maxScale=1` + no `minScale` was causing scale-to-zero idle cold starts. The Backend/Cloud Run data did not support that as stated — but it also did not rule it out. 0% of the 112 *sampled* hourly points were at zero instances, but the query returned only 112 of the ~168 hourly points a full 7-day window should have, and Cloud Run's `instance_count` metric reports gaps rather than zero-valued samples for periods with no running instances — the missing 56 hours (~8/day, a plausible nightly-idle shape) are not established as either zero or non-zero by this data, so whether the service actually scaled to zero this week remains unresolved. The 13 measured cold-start events (7,146.9-20,111.6 ms, p95 20,111.6 ms) are consistent with lining up with revision deployments during the week rather than idle-to-live transitions — 13 distinct revision-keyed startup events is consistent with 13 deployed revisions — but this was not directly verified against actual revision-creation timestamps, so it remains an inference from the metric's shape, not a confirmed cross-reference. Peak concurrency (11.5, hourly p95) is nowhere near Cloud Run's 80-per-instance default, so `maxScale=1` is confirmed not a live bottleneck today, independent of the scale-to-zero question. This changes what a `minScale` recommendation is *for* (see #3) — it should not be sold as a confirmed fix for cold starts this investigation directly observed happening from idle, since it did not establish whether that happened at all.

1. **Fix the uncached Firestore hot paths — live draft, mock draft, and admin full-collection streams — on their own merits, and investigate the cache-invalidation refetch pattern in parallel.** Task 3's web-app inventory and Task 4's aggregate metrics (2,676,060 reads / 136,071 writes / 29 deletes over 7 days) were initially read as pointing at these uncached hot paths as the dominant driver of the read volume — but that attribution doesn't survive the same magnitude test the report correctly applied to rule out the scheduled jobs: at ≈382,300 reads/day, a once-per-season live draft (~390-420 reads total) and even a generous few dozen mock-draft sessions/day (~57 reads each) land two to three orders of magnitude short (see the Aggregate volume Interpretation above). These fixes are still worth doing — the paths are genuinely wasteful and redundant regardless of their share of total volume — but **investigating/measuring the unscoped `clear_data_cache()` → unfiltered master-key refetch pattern** (also detailed above: `data_service.py:78` wipes the entire `_DATA_CACHE` on any remote-invalidation signal, and the next unscoped `load_data()` call refetches `nfl_games`/`nfl_standings` back to 2013, unfiltered — a plausible ~4,000-4,500-document rebuild, potentially triggered dozens of times a day by `winspool-live-scores`' up to 288 daily signals) should be treated as an equally or more urgent parallel action, not a resolved question. Concrete, scoped fixes, cheapest first:
   - Scope `clear_data_cache()`'s remote-invalidation call site (`data_service.py:78`) to the year that actually changed instead of wiping every cached year plus the unscoped `'all'` key, and confirm (with real measurement — request/instance logging or a Firestore read-count check before/after) how often the unscoped rebuild actually fires and how many documents it costs. This is the investigation this report could not complete from code-reading alone, and — if confirmed — is likely the single highest-leverage fix in this list.
   - Dedupe `get_season_projection_blended()` and `get_season_projection_dual()` (`services/draft_service.py:153,159`) — they independently re-fetch `preseason_predictions` and `consensus_projections`, 4 raw reads where 2 would do. This alone removes half of the live-draft pick path's projection reads.
   - Cache `preseason_predictions` / `consensus_projections` at the process level (`services/data_service.py:390,412`). These only change once a day at most, driven by `winspool-predict-daily`, yet are read uncached on every pick and every mock-draft bot pick — a real reduction to both the live-draft pick path (~390-420 round trips/draft, 13-14/pick) and the mock-draft session (~57 reads/session), even though neither is the dominant driver of the aggregate total.
   - Avoid the chat double-RPC in `services/chat_service.py` (`ref.add()` followed by a separate `doc_ref.get()` to read back the same data) by constructing the broadcast payload locally instead of reading it back — halves the ~4 chat RPCs/pick contributed by `_broadcast_pick_messages()`.
   - Cache the `elo_history` / `nn_weekly_accuracy` full-collection `.stream()` reads (`services/cache_service.py:399-441,497-535`) — admin-only and low write frequency, so a simple process-lifetime or short-TTL cache is low-risk.
   - Leave `_CACHE_TTL_SECONDS` at 3600s (Task 5's finding stands): every write path feeding `load_data()`'s bundle already signals invalidation within ~60s via `metadata/cache_control`, and none of the hot paths above route through that cache layer at all, so tuning the TTL would not touch this problem.

2. **Investigate the `winspool-live-scores` 18-day execution gap (2026-08-22 to 2026-09-09) — highest severity, and an operator task, not a code fix.** This job ran zero times for ~18 days squarely inside its own documented in-season window (Aug/Sept 1 - Feb 10 per CLAUDE.md), meaning live game scores and standings went unrefreshed for roughly 2.5 weeks during the season before resuming its exact 5-minute cadence on 2026-09-10. Root cause (Cloud Scheduler trigger health, IAM, quota, or something else) was out of scope for this investigation and remains undiagnosed — flagging it here is this report's contribution, not a fix (see the Firestore Usage section's Operational anomaly callout for why the existing failure-based alert policy couldn't have caught this on its own). One thing worth checking first given the job's own history: an earlier, unnarrowed version of this same job was independently measured at ~179,000 writes/day (~9x the Firestore free-tier daily quota) before the trailing-7-day-window narrowing was added — worth ruling out a quota-related trigger failure as part of the root-cause investigation.

3. **Cloud Run `minScale=1` — recommend it as cheap insurance against idle-triggered cold starts this investigation could not rule out, not as a confirmed fix for a diagnosed cause.** The measured cold-start events are consistent with being deployment-triggered (a new revision's first instance boots regardless of `minScale`), but this was not directly verified against revision-deployment timestamps. And whether the service also scaled to zero during this window is unresolved: the instance-count query is missing 56 of an expected 168 hourly samples (~8 hours/day), and Cloud Run reports gaps rather than zero-valued samples for periods with no running instances, so those missing hours cannot be assumed non-zero. Given that ambiguity, `minScale=1` is worth recommending regardless of which cause turns out to be true: it protects against idle cold starts if the missing-sample hours do turn out to be scale-to-zero periods, and it's cheap insurance against future traffic growth and low-traffic windows this investigation didn't happen to catch either way.
   - **Cost, quantified against Cloud Run's published Tier-1 rates.** Request-based ("CPU allocated only during request processing") active billing: $0.000024/vCPU-second, $0.0000025/GiB-second. For `minScale`'d minimum instances sitting idle (not processing a request), Cloud Run bills a separate, lower minimum-instance idle rate — roughly $0.0000025/vCPU-second (≈10x cheaper than the active CPU rate) and $0.00000025/GiB-second (≈10x cheaper than the active memory rate; the previous version of this estimate mistakenly reused the *active* memory rate for the idle case, understating the discount memory actually gets). For a `minScale=1` instance (1 vCPU + 512Mi = 0.5 GiB) idle for a full 730-hour (2,628,000-second) month: CPU = 2,628,000 × $0.0000025 ≈ $6.57; memory = 2,628,000 × 0.5 × $0.00000025 ≈ $0.33; **total ≈ $6.90/month**. Worst case — "CPU always allocated" instance-based billing (no evidence the service uses this), which prices lower per unit than request-based since it assumes continuous allocation: CPU ≈ $0.000018/vCPU-second, memory ≈ $0.000002/GiB-second. For the same instance running continuously all month: CPU = 2,628,000 × $0.000018 ≈ $47.30; memory = 2,628,000 × 0.5 × $0.000002 ≈ $2.63; **total ≈ $49.93/month**, before any remaining Cloud Run free-tier credit. Given this week's own data shows the single instance already ran continuously without ever hitting zero, the realistic *incremental* cost of formalizing that via `minScale=1` this particular week would be close to $0 — the ~$6.90/month figure is what the insurance costs in a week where it would actually matter. Either way, the conclusion is unchanged: `minScale=1` is cheap.
   - Leave `maxScale=1` unchanged for now — peak concurrency (11.5, hourly p95) isn't close to Cloud Run's 80-per-instance default — but see the alert threshold below for when to revisit it.

4. **Core Web Vitals: no action needed on LCP/CLS; treat the INP/TBT gap as a measurement limitation to close, not a finding.** All 4 measured LCP figures (241-631 ms) and CLS figures (0.005-0.01) comfortably clear Google's "good" thresholds (<2.5s, <0.1) — no fix is warranted on the metrics that were measurable. Two things worth flagging rather than acting on: (a) all four runs were unthrottled/best-case (1x CPU, no network throttling against the live service), not representative of a user on a slow connection; (b) INP and TBT could not be measured at all with the tooling available in this environment — a real gap in this investigation, not a "good" result being implied. Recommend a follow-up pass with Lighthouse's own performance category (a different `chrome-devtools-mcp` version or the standalone `lighthouse` CLI) or a synthetic-interaction trace before treating Core Web Vitals as fully clean.

5. **Suggested alert thresholds going forward**, one per metric this report actually gathered, each referenced to its real baseline:
   - **Request latency (2xx):** baseline p50 = 41.3 ms, p95 = 984.7 ms. Alert if p95 > 2,000 ms sustained over a rolling window (~2x today's baseline).
   - **Cold-start / container-startup latency:** baseline p95 = 20,111.6 ms across 13 revision-startup events (range 7,146.9-20,111.6 ms). Alert if any revision's startup latency exceeds 25,000 ms — above today's observed worst case, sized to catch a genuine regression rather than normal variance.
   - **Peak concurrency vs. `maxScale=1` headroom:** baseline 11.5 (hourly p95-aligned max) against Cloud Run's 80-per-instance default. Alert if hourly peak concurrency > 40 (50% of that default) — an early warning that `maxScale=1` is becoming a real capacity constraint, well before requests start queueing near 80.
   - **Idle/scale-to-zero behavior:** baseline 0% of 112 *sampled* hours at zero instances this window — but 56 of the expected 168 hourly samples returned no data at all rather than a confirmed non-zero reading (see Backend/Cloud Run above), so this baseline describes the sampled hours only, not the full week. Alert if the service is observed at zero running instances for >15 consecutive minutes during in-season hours — turns the motivating finding's untested hypothesis into a monitored condition instead of a one-week snapshot, and is the concrete trigger for revisiting `minScale` (#3) if it ever fires.
   - **Firestore document reads:** baseline 2,676,060 over 7 days (≈382,300/day) — already ≈7.6x the Firestore free tier's 50,000-reads/day allowance. Alert if daily reads exceed ~500,000/day (~30% above today's daily average).
   - **Firestore document writes:** baseline ≈90,000-95,000/week (estimated; ≈13,000/day) attributed to `winspool-live-scores` alone, against a historical ~179,000/day figure from an earlier unnarrowed version of that same job (~9x the Firestore free tier). Note this can't actually be alerted on *per job* today: Cloud Monitoring's Firestore metrics carry no per-caller/per-job breakdown (see the Firestore Usage section), so a per-job threshold would require new custom instrumentation — e.g. each job emitting its own write count as a custom metric — that doesn't exist yet. Until that instrumentation exists, alert on the project-wide daily write total instead: baseline ≈19,438/day (136,071 over 7 days); alert if daily writes exceed 50,000/day — well above today's project-wide average but well below the previously-fixed ~179,000/day problem level, so it catches a regression back toward it.
   - **Scheduled-job liveness (the direct, targeted fix for the gap found in #2):** alert if `winspool-live-scores` logs zero executions in any rolling 15-minute window during its documented in-season window (Aug/Sept 1 - Feb 10) — sized to its own ~5-minute cadence, this would have caught the real 18-day gap within 15 minutes instead of it running silently for over two weeks. Apply the same pattern, sized to each job's own cadence, to the other three: `winspool-sync-daily` / `winspool-predict-daily` (alert if no execution in 25 hours), `winspool-schedule-kickoffs` (alert if no execution in 8 days).
   - **LCP:** baseline range 241-631 ms across the 4 measured page/viewport combinations (all "good"). Alert if a measured LCP exceeds 1,500 ms — still under the 2.5s "good" threshold, but 2-6x today's baseline, giving an early warning before crossing into "needs improvement."
   - **CLS:** baseline range 0.005-0.01. Alert if CLS exceeds 0.05 — still under the 0.1 "good" threshold, but 5-10x today's baseline.
   - **INP/TBT:** no baseline exists (tooling gap, see #4). No threshold can be set until a measurement method is in place — this is itself a to-do, not a metric to alert on yet.
