## API/data-contract decisions to make deliberately (not yet acted on)

- **A pushed ATS bet reports `is_correct_ats: null`, identical to an
  unplayed game.** `routes/api_routes.py::get_prediction_explain`'s ATS
  grading only sets `is_correct_ats` when `grade_bet()` returns `"win"` or
  `"loss"`; a `"push"` result falls through to `None`, the same value used
  for "game hasn't happened yet." The "Why TEAM?" modal (Task 5) uses
  `null` as its "don't render a badge" signal, so a pushed game silently
  shows no ATS badge at all rather than a distinct push indicator. This was
  plan-mandated (verbatim from the Task 4 brief, which didn't specify push
  behavior) and pushes are rare, so it shipped as-is. Decide deliberately
  whether to add a third rendered state (e.g. a neutral "· PUSH" badge) or
  leave push and "not yet played" visually identical — currently no one has
  chosen either on purpose.
- **`pred_ats_pick` team-normalization mismatch silently defaults to the
  "away" side.** `routes/api_routes.py::get_prediction_explain`:
  `side = "home" if _normalize_team(str(pred_ats_pick)) == ht else "away"`
  — if `pred_ats_pick` ever normalizes to neither team in the matchup (a
  corrupted or stale prediction record), it silently grades as if the pick
  were the away team rather than erroring or returning `None`. Low
  real-world risk since `pred_ats_pick` is generated by the same pipeline
  for the same two-team key, so it should always be one of the two teams in
  practice — but if this Track's grading is ever the basis for money-moving
  logic (payouts, leaderboards) rather than just a UI badge, this silent
  fallback should become a hard failure instead.
- **A tied game leaves `is_correct` null, same as an unplayed game — this
  one is deliberate, not a gap.** `actual_winner = ht if res > 0 else (at
  if res < 0 else None)` in the same function correctly has no straight-up
  winner to grade against on a tie. Noting only so it reads as an
  intentional design choice next time someone notices the modal shows no SU
  badge for a tied game and wonders if it's a bug.

## Performance

- **`GET /api/predictions/explain` now runs `load_data()` unfiltered on
  every request**, not just on the old vegas_line-fallback path. Task 4's
  grading logic needs the game row for SU/ATS grading, so the call itself
  is justified — but the season/week match mask runs two
  `.apply(_normalize_team)` passes over the *full multi-season* games frame
  on every modal open, rather than pre-filtering by `season`/`week` first.
  Low real impact today (an on-click admin/player modal, and `load_data()`
  itself is cached) — worth tightening if this endpoint's call volume ever
  grows past "someone clicks a modal."

## Test coverage gaps

- **Task 4's test fixture (`tests/test_api_endpoints.py::_mock_games_df`)
  encodes an internally-inconsistent spread-sign convention and doesn't
  actually pin the ATS win/loss/push direction.** The fixture uses
  `spread_line: -2.5` with `home_team: "KC"`, `pred_winner: "KC"`,
  `pred_ats_pick: "KC"`, `model_spread: -3.0` — this codebase's convention
  is positive `spread_line` = home favored
  (`services/betting_screener_service.py`'s module docstring;
  `schedule_explain.js`'s `_fmtLine`), so the fixture actually depicts
  Vegas and the model both favoring the *away* team while the prediction
  picks home. Both existing ATS test assertions would still pass under a
  hypothetical spread-sign-negation bug, since `|margin| = 3 > |line| =
  2.5` holds on the same side either way — they exercise that `grade_bet()`
  gets called and its result maps to a bool, without pinning the sign
  convention itself. Contained risk today: `grade_bet()`'s own tests
  (`tests/test_betting_screener_service.py`) pin the convention correctly.
  Follow-up: add one correctly-signed test case for the SU-correct/ATS-wrong
  divergence (home favored by 3, wins by 1) — that's the exact scenario the
  two-badge UI in the "Why TEAM?" modal exists to display, and it's
  currently untested end-to-end.

## Local dev environment hygiene (not code, but bit this Track twice)

- **Orphaned `uvicorn --reload` worker processes survive after their
  supervisor dies and keep serving stale code with no way to auto-reload.**
  This caused a real false-negative during Task 5's manual browser
  verification: two stray worker processes from earlier subagent sessions
  in this worktree were still bound to port 8000, silently serving
  pre-Task-5 static files, which made a correct implementation look broken
  until the orphans were found (via `Get-NetTCPConnection` /
  `Get-CimInstance Win32_Process`, not plain `netstat`+`Get-Process`, which
  disagreed with each other because the socket-holding process was a
  `multiprocessing.spawn_main` child of an already-dead `uvicorn.exe`
  parent) and killed. Worth remembering next time local verification "shows
  the old behavior" unexpectedly after a code change: check for a stray
  server before assuming the diff is wrong.
- **This repo's `.git/worktrees/` has ~10 stale entries that
  `git worktree prune` can't delete** (`baseline-check`, `cleanup-docs`,
  `feature-version-stamp-promotion-gate` and `-1`, `followup-spec`,
  `injury-aware-roster-value`, `preseason-draft-snapshot`,
  `ui-tests-admin-flows`, `ui-tests-player-flows`, `ui-tests-sdd`, and now
  this Track's own `model-prediction-pipeline-tail`) — `prune` correctly
  unregisters them from `git worktree list` but fails to delete the
  physical `.git/worktrees/<name>` admin directory with `Permission
  denied`, consistent with OneDrive (this repo lives under
  `OneDrive\Documents\...`) holding a file lock. Harmless clutter, not
  blocking any git operation observed so far, but worth a manual cleanup
  pass — likely needs OneDrive paused or a reboot to release the locks
  before `git worktree prune` can finish the job.
